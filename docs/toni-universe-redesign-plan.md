# Enterprise FDE Delivery Galaxy 重设计实施方案

> 文档状态：沉浸式宇宙视觉纠偏与实施稿 v1.2  
> 适用项目：`toni.asia / AILA`  
> 产品名：`FDE Delivery Galaxy`  
> Canonical route：`/toni-universe`  
> 兼容策略：如未来需要保留 `/fde`，只允许由 `/fde` 永久跳转到 `/toni-universe`  
> 当前范围：Enterprise FDE 业务骨架、深空粒子星团、关系光纤、镜头聚焦、结构化移动列表、静态数据契约与验收基线已经落地；更完整的 engagement 本体和 URL 深链状态按后续阶段实施。

## 0. 2026-07-10 视觉纠偏结论

用户参考录像的关键不是“节点可旋转”，而是一个具有强烈空间质量感的宇宙：大量微粒组成密集星团，关系形成发光纤维，旋转后整体轮廓显著变化，镜头能够穿过星团而不是只靠近单个球体。

本轮把以下内容设为强制视觉契约：

- 页面使用暗色深空环境，不再以暖白关系图作为最终呈现。
- 27 个业务节点只作为可交互语义锚点；视觉密度由数千颗程序化粒子、次级光点和内部结构纤维承担。
- Enterprise FDE 是画面最大的交付星团，不允许用一个放大的 `SphereGeometry` 代替。
- Discover、Design、Build、Deploy、Operate、Compound 形成纵向交付脊柱；旋转到侧面时必须能看出前后错位的多个团簇。
- 39 条语义关系展开为成束曲线光纤，并配合能量点移动；禁止全部使用两点直线。
- 默认只显示核心和少量导航标签；能力与证据标签在 hover、搜索或聚焦后出现。
- 宇宙占据完整视口，介绍、筛选、详情和阶段导航都是覆盖式 HUD，不能再用三栏布局压缩 Canvas。
- 使用 GSAP 管理入场、相机航行和面板退场；使用 Bloom、加色混合、星云纹理和多层星场建立深度。
- 移动端首屏直接进入宇宙，降低 DPR 和粒子密度，但保留核心视觉结构。

视觉验收底线：默认截图不能一眼数清所有节点；主星团必须由粒子和纤维形成；桌面总览高度接近满屏；聚焦后仍保留邻近星团作为方向参照；页面不能退化为“几个球加连线”。

## 1. 目标契约

### 1.1 目标

把原先面向个人作品、工具和泛能力展示的 Universe 方案，重构为一个企业 FDE（Forward Deployed Engineering，前沿部署工程）交付系统地图。

最终页面必须让企业决策者和交付团队在同一张三维关系图中看清：

- 正在解决哪一个业务问题。
- 哪些客户角色、业务流程、系统、数据和约束参与其中。
- 项目当前处于哪个交付阶段。
- 每个阶段产生了哪些可审计工件。
- 哪些关系构成了交付路径、依赖、风险和结果证据。
- 一个已交付案例如何连接到可复用的工程能力和下一次扩展机会。

### 1.2 边界

本方案只定义 FDE 业务地图，不再承担以下职责：

- 不做 Toni 个人经历总览。
- 不做泛化的产品作品集。
- 不做工具目录或功能货架。
- 不用“智能、赋能、创新、生态”等空泛标签代替业务实体。
- 不生成没有来源依据的客户关系、结果指标或交付状态。
- 不建设多人编辑知识图谱、客户后台或实时项目管理系统。
- 不接入新的外部服务来动态生成节点和关系。

### 1.3 做法

- 使用真实企业交付对象作为节点，而不是“案例 / 工具 / 实验 / 方法”四类内容栏目。
- 使用客户、流程、系统、角色、交付阶段、工件、部署和结果证据组成业务本体。
- 使用 Three.js 建立真正可旋转、缩放、聚焦的三维节点关系场景。
- 使用 GSAP 负责镜头航行、聚焦、路径追踪和阶段切换，不把动画塞进 React 渲染循环。
- 使用暗色深空、品红/紫罗兰/青色/琥珀局部高光，直接承接录屏中的高密度星团体验，同时让色彩对应 FDE 交付层级和关系类型。
- 使用本地强类型数据和静态契约检查保证节点、关系、阶段和证据真实可追踪。

### 1.4 验收

完成后应能通过以下事实证明方案落地正确：

1. 页面首屏明确显示 FDE 交付地图，而不是个人品牌或泛技术展示。
2. 桌面端存在可操作的三维旋转、缩放、平移和节点聚焦。
3. 图中存在多个高密度业务簇，节点尺寸有可解释差异，关系线能显示依赖和交付流向。
4. 用户可以从客户问题追踪到交付阶段、责任角色、系统依赖、工件和结果证据。
5. 用户可以从一个案例切换到“交付阶段视图”“系统拓扑视图”和“结果证据视图”。
6. 低性能设备、移动端、键盘用户和减少动态效果用户存在可用路径。
7. `npm run test:baseline`、`npm run lint` 和 `npm run build` 通过。
8. 浏览器按本文定义的桌面与移动路径完成验证。

### 1.5 失败方式

如果真实案例内容、客户授权或指标证据不足，不得用推测补齐。应显示为“待确认”“未公开”或不进入公开图谱，并在内容盘点中列出缺口、责任人和下一步。

## 2. 一句话产品定义

`FDE Delivery Galaxy` 是一张可探索的企业交付系统地图：它把客户业务、现场角色、工作流、数据系统、工程工件、部署阶段和结果证据组织为一个高密度三维节点网络，用来解释 FDE 团队如何进入现场、建立问题契约、完成集成、推动上线并形成可验证结果。

## 3. 战略结论

### 3.1 核心业务必须是 FDE

页面的主角不是 Toni，也不是某一项技术。主角是企业问题从发现到上线的完整交付关系。

页面首先回答：

> FDE 团队如何与客户一起，把一个跨角色、跨流程、跨系统的问题变成可上线、可运营、可验收的工程结果？

页面其次回答：

> 已完成的案例证明了哪些交付能力，这些能力可以在哪些相邻场景复用？

### 3.2 录屏灵感的正确转译

录屏不是情绪参考，而是本项目的空间体验基准。必须保留：

- 深黑背景和多层星场形成的真实空间纵深。
- 多个由数百到上千微粒组成的高密度发光星团。
- 核心光核、次级光点、粒子云、星云和关系纤维形成的多层亮度结构。
- 关系线以曲线光纤束跨越团簇，交付主链亮于能力和证据关系。
- 用户自由旋转时，同一系统从正面和侧面呈现完全不同的整体轮廓。
- 聚焦后镜头沿弧线进入当前团簇，非相关内容退到深空但不完全消失。
- 标签只承担导航和解释，不覆盖每一个视觉粒子。

AILA 的差异不再是把宇宙改成白色，而是把录屏的视觉冲击转译为 Enterprise FDE 的业务结构：中心星团代表交付质量，纵向光纤脊柱代表从现场到生产再到复用的连续路径，外围团簇代表能力和已经发生的交付证据。

### 3.3 不再采用的旧结构

以下旧结构从产品定义中移除：

- 案例星系。
- 工具星系。
- 实验星系。
- 方法星系。
- 以个人为中心的能力辐射图。
- 泛化的“获客、销售、验证、经营”等无上下文能力标签。
- 仅为作品页、工具页和课程页导流的高级导航定位。

这些内容只有在能够转换成真实 FDE 实体、交付工件或案例证据时，才允许进入新图谱。

## 4. FDE 业务模型

### 4.1 FDE 在本项目中的定义

FDE 是一支长期贴近客户业务现场的工程交付能力。它不只提交一个软件功能，而是共同承担问题澄清、流程重构、系统集成、现场试运行、上线验收和持续扩展。

本项目中的 FDE 必须同时具备四个属性：

1. **现场性**：从真实操作、数据和组织约束出发，而不是从抽象需求列表出发。
2. **工程性**：产出可运行系统、集成、配置、测试和运维工件，而不是只产出建议。
3. **结果性**：交付由明确指标、验收记录和运行证据证明。
4. **嵌入性**：FDE 与客户负责人、业务人员、数据负责人、安全团队和运维团队共同推进。

### 4.2 FDE 交付对象

FDE 交付的不是“一个模型”或“一个页面”，而是一组能够共同运行的企业对象：

- 一个被清楚定义的业务问题。
- 一个有责任人的业务流程。
- 一组明确的数据来源和系统边界。
- 一套可执行的解决方案和集成契约。
- 一条从试点到上线的部署路径。
- 一套被客户接受的运行与交接方式。
- 一组可审计的结果证据。

## 5. 目标用户与主要任务

| 用户 | 进入页面时的问题 | 主要任务 | 成功状态 |
|---|---|---|---|
| 企业决策者 | 这支团队能否处理我的复杂业务问题 | 查看相似案例、结果证据和扩展路径 | 理解合作范围并进入诊断会谈 |
| 业务负责人 | 交付会改变哪些流程和责任 | 查看流程、角色、阶段和验收门 | 能识别自己需要投入的人员与数据 |
| 技术 / 数据负责人 | 需要连接哪些系统，风险在哪里 | 查看系统拓扑、接口、数据和约束 | 能判断集成可行性与前置条件 |
| 安全 / 合规负责人 | 哪些数据和操作进入系统 | 查看数据边界、审批、风险和审计工件 | 能确认控制点和未决事项 |
| FDE 团队 | 当前项目处于哪里，下一步由谁负责 | 查看阶段、阻塞、工件和责任关系 | 快速恢复项目上下文 |
| 潜在合作伙伴 | 哪些能力已被真实交付证明 | 查看案例链路和可复用交付模式 | 找到具体协作入口 |

## 6. 企业实体本体

图谱必须由业务实体驱动。每一个节点都要有明确类型、来源、状态、责任和关系，不允许只为了增加视觉密度而创建装饰节点。

### 6.1 一级实体类型

| 实体类型 | 业务含义 | 典型节点 | 必填信息 | 默认视觉权重 |
|---|---|---|---|---|
| `account` | 客户或业务单位 | 某咨询业务线、某电商运营团队 | 名称、行业、公开级别 | 最大簇中心之一 |
| `engagement` | 一次有边界的 FDE 交付 | 问卷决策系统交付、爆品筛查试点 | 阶段、负责人、目标、状态 | 全图核心节点 |
| `business_problem` | 被批准进入交付的问题 | 报告产出慢、选品依赖人工 | 当前基线、影响、责任人 | 大节点 |
| `workflow` | 被改变的真实业务流程 | 问卷回收至管理报告、选品至投放 | 起点、终点、操作角色 | 中大节点 |
| `role` | 客户或交付责任角色 | 业务发起人、运营人员、数据负责人 | 组织、责任、参与阶段 | 中节点 |
| `system` | 参与交付的应用或平台 | CRM、表单系统、ERP、内容工作台 | 所有者、接口、环境 | 中节点 |
| `dataset` | 输入、输出或证据数据 | 问卷结果、SKU 数据、素材库 | 来源、敏感级别、刷新方式 | 小到中节点 |
| `constraint` | 决定方案边界的约束 | 数据不可出域、人工审批必需 | 类型、影响、处理状态 | 中节点，警示边框 |
| `delivery_stage` | FDE 生命周期阶段 | 现场发现、试点、上线 | 进入条件、退出条件 | 阶段骨架节点 |
| `artifact` | 可审计交付工件 | KPI 契约、数据字典、UAT 记录 | 版本、负责人、状态 | 小到中节点 |
| `deployment` | 可运行的部署实例 | 试点环境、生产工作台 | 环境、日期、版本、状态 | 中大节点 |
| `metric` | 业务或运行指标 | 处理周期、人工步骤、采纳率 | 基线、目标、口径、证据 | 中节点 |
| `evidence` | 证明结果或决策的记录 | 验收单、运行日志、指标快照 | 来源、日期、可见级别 | 小节点，高可信标识 |
| `risk` | 影响范围、时间或质量的风险 | 数据缺口、接口未授权 | 严重度、责任人、缓解状态 | 小到中节点，风险色 |
| `expansion` | 已确认的后续扩展机会 | 新业务线、更多地区、更多流程 | 前置条件、价值、状态 | 外围成长节点 |

### 6.2 节点尺寸规则

节点尺寸必须体现业务重要性，不按视觉喜好手工设置。

推荐使用可解释的权重模型：

```text
nodeSize = typeBase
         + relationshipDegreeWeight
         + businessImpactWeight
         + evidenceWeight
         + stageCriticalityWeight
```

约束：

- `engagement`、`account` 和关键 `business_problem` 是每个簇内最大的节点。
- 连接多个系统和工件的核心 `workflow` 可以超过普通角色节点。
- 已有结果证据的 `metric` 比只有目标值的指标更大、更实。
- 高连接度不自动等于高价值，必须与业务影响或阶段关键性共同决定。
- 节点尺寸在统一范围内截断，避免一个节点吞没整个场景。
- 同一实体在不同视图中可调整表现，但业务权重来源不变。

### 6.3 节点状态

所有主要节点必须使用统一状态，不允许用自由文本制造无法筛选的状态：

- `proposed`：已提出，未确认进入交付。
- `validated`：问题、范围或数据已经确认。
- `in_progress`：正在交付。
- `blocked`：存在明确阻塞。
- `accepted`：已通过客户验收。
- `operational`：已进入稳定运行。
- `expanded`：已进入新范围或新业务线。
- `archived`：保留记录，不再活动。

## 7. FDE 交付阶段

交付阶段构成整张图的时间骨架。每个 `engagement` 必须连接到当前阶段，并保留已完成阶段的关键工件和证据。

| 阶段 | 核心问题 | 主要活动 | 必交工件 | 退出门 |
|---|---|---|---|---|
| 0. 机会资格确认 | 是否值得进入现场 | 识别业务影响、发起人、预算和时间窗口 | 机会简报、初始风险表 | 发起人同意进入发现阶段 |
| 1. 现场发现 | 真实工作如何发生 | 访谈、跟岗、流程观察、数据抽样 | 当前流程图、角色图、数据清单 | 事实链被业务负责人确认 |
| 2. 问题与指标契约 | 到底解决什么，如何判断成功 | 定义问题边界、基线、目标、非目标 | 问题陈述、KPI 契约、范围说明 | 指标口径和责任人签字确认 |
| 3. 系统与风险映射 | 需要连接什么，受什么限制 | 系统盘点、接口验证、安全和合规评审 | 系统拓扑、数据字典、风险登记册 | 关键数据与接口路径可执行 |
| 4. 方案与试验设计 | 最小可上线方案是什么 | 方案评审、原型、集成契约、试点设计 | 方案说明、原型、接口契约、试点计划 | 客户批准试点范围 |
| 5. 嵌入式构建 | 如何在现场约束下完成系统 | 开发、配置、数据处理、联调、演练 | 可运行版本、测试记录、操作草案 | 进入客户试用条件满足 |
| 6. 试点与 UAT | 真实用户能否完成目标任务 | 试运行、反馈、缺陷处理、验收测试 | UAT 记录、问题清单、培训材料 | 业务负责人接受上线 |
| 7. 上线与运行 | 系统能否稳定产生结果 | 发布、监控、支持、事件处理 | 发布记录、运行手册、支持矩阵 | 稳定运行并形成结果证据 |
| 8. 交接与扩展 | 能否被客户接管并扩大价值 | 权限移交、知识转移、复盘、扩展评估 | 交接包、结果报告、扩展提案 | 责任完成移交或进入新 engagement |

### 7.1 阶段关系规则

- 阶段不是页面筛选标签，而是有进入条件、退出门和工件要求的交付契约。
- 一个 engagement 同一时刻只能有一个主要当前阶段。
- 阶段可以回退，但必须记录回退原因和新增风险。
- 关键工件未完成时，不允许在图谱中把阶段显示为已完成。
- “上线”不等于“完成”；必须继续连接运行证据、交接和扩展节点。

## 8. 角色与责任网络

### 8.1 客户侧角色

| 角色 | 核心责任 | 必须连接的实体 |
|---|---|---|
| Executive Sponsor | 业务优先级、资源和最终决策 | account、engagement、metric、expansion |
| Business Owner | 流程结果、范围和验收 | business_problem、workflow、artifact、evidence |
| Frontline Operator | 提供真实操作路径并参与试点 | workflow、system、UAT 工件 |
| Data Owner | 数据授权、口径和质量 | dataset、system、constraint、metric |
| IT / Integration Owner | 环境、接口和上线支持 | system、deployment、risk、artifact |
| Security / Compliance | 数据边界、审批和审计要求 | constraint、risk、artifact、deployment |
| Operations Owner | 上线后的运行和支持 | deployment、runbook、evidence、incident |

### 8.2 FDE 侧角色

| 角色 | 核心责任 | 必须连接的实体 |
|---|---|---|
| FDE Lead | 目标契约、客户协调、阶段退出门 | engagement、business_problem、metric、stage |
| Forward Deployed Engineer | 现场发现、方案、集成和交付 | workflow、system、dataset、artifact、deployment |
| Product / Solution Engineer | 可复用能力、产品边界和工程质量 | artifact、system、deployment、risk |
| Data Engineer / Analyst | 数据映射、转换、口径和结果验证 | dataset、metric、evidence、artifact |
| QA / Reliability Owner | 测试、发布、监控和故障闭环 | UAT、deployment、evidence、risk |

### 8.3 责任表达

角色关系不能只显示“参与”。至少区分：

- `SPONSORS`：提供业务授权与资源。
- `OWNS`：对业务结果或系统负责。
- `OPERATES`：日常执行流程或使用系统。
- `APPROVES`：对范围、风险、上线或验收作决定。
- `BUILDS`：负责实现或集成。
- `VALIDATES`：验证数据、行为或结果。
- `SUPPORTS`：承担上线后的支持责任。

## 9. 交付工件体系

工件是 FDE 可信度的核心。页面不只显示“做了什么”，还要显示“用什么证据完成了阶段退出”。

### 9.1 发现与定义工件

- 机会简报。
- 访谈记录索引。
- 当前流程图。
- 角色与责任图。
- 问题陈述。
- 范围与非目标。
- KPI 契约。
- 数据来源清单。

### 9.2 方案与工程工件

- 目标流程图。
- 系统拓扑。
- 数据字典与字段映射。
- 接口与集成契约。
- 架构决策记录。
- 风险登记册。
- 原型与验证记录。
- 测试计划和测试结果。

### 9.3 上线与运营工件

- 试点计划。
- UAT 记录。
- 发布清单。
- 部署记录。
- 运行手册。
- 支持与升级矩阵。
- 监控定义。
- 结果报告。
- 交接包。
- 扩展提案。

### 9.4 工件公开级别

每个工件必须定义可见级别：

- `public_summary`：可公开名称和摘要。
- `public_redacted`：可公开脱敏结构或截图。
- `private_reference`：只显示存在，不显示内容。
- `hidden`：不进入公开图谱。

## 10. 首批案例模型

首批案例应来自已经存在、可被验证的企业交付内容。未确认客户名称时使用行业和业务单元描述，不虚构品牌名。

### 10.1 案例 A：咨询问卷到经营决策系统

**业务问题**

- 问卷数据分散在不同文件和工具中。
- 统计、图表和管理报告依赖人工整理。
- 结论口径难以复核，报告交付周期不稳定。

**关键实体**

- Account：咨询服务业务线。
- Engagement：问卷统计与决策报告交付。
- Roles：业务发起人、咨询顾问、分析负责人、数据负责人、FDE Lead、FDE Engineer。
- Workflow：问卷设计 → 回收 → 清洗 → 统计 → 图表 → 报告 → 管理评审。
- Systems：表单系统、文件存储、分析工作台、报告输出。
- Datasets：问卷结果、题目字典、分组口径、历史报告。
- Artifacts：流程图、字段映射、指标口径、报告模板、UAT 记录、运行手册。
- Metrics：处理周期、人工步骤数、返工次数、报告准时率。
- Evidence：验收记录、运行批次、结果快照。

**关系主链**

```text
业务发起人 SPONSORS engagement
业务负责人 OWNS 问卷到报告 workflow
workflow READS_FROM 问卷结果 dataset
FDE Engineer BUILDS 分析工作台 deployment
deployment PRODUCES 管理报告 artifact
业务负责人 VALIDATES UAT 记录
结果快照 EVIDENCES 处理周期 metric
```

### 10.2 案例 B：电商爆品筛查与投放决策

**业务问题**

- 候选商品数量大，初筛依赖个人经验。
- 商品、价格、销量、竞争和内容信号分散。
- 从发现候选到投放决策缺少统一证据链。

**关键实体**

- Account：电商运营团队。
- Engagement：候选商品筛查与试点决策。
- Roles：运营负责人、选品人员、投放负责人、数据负责人、FDE 团队。
- Workflow：候选收集 → 数据补全 → 规则筛查 → 人工复核 → 小规模验证 → 投放决策。
- Systems：商品数据源、运营表格、筛查工作台、投放记录系统。
- Datasets：SKU 主数据、价格区间、销量信号、竞争信号、投放结果。
- Constraints：数据刷新频率、平台字段变化、最终决策必须人工批准。
- Artifacts：筛查规则、数据字典、候选评分说明、试点方案、决策记录。
- Metrics：候选处理时间、进入复核比例、试点转化率、无效投放比例。

**关系主链**

```text
商品数据源 FEEDS SKU dataset
筛查 workflow READS_FROM SKU dataset
人工审批 constraint GOVERNS 投放决策
筛查工作台 deployment SUPPORTS 筛查 workflow
试点结果 evidence VALIDATES 候选评分 artifact
运营负责人 APPROVES 投放决策
```

### 10.3 案例 C：商用电商创意生产工作台

**业务问题**

- 活动需求、商品信息、素材和审核意见分散。
- 多尺寸、多渠道素材生产存在重复劳动。
- 从需求到发布缺少版本、审批和结果追踪。

**关键实体**

- Account：电商内容与设计运营团队。
- Engagement：活动创意生产流程重构。
- Roles：活动负责人、设计人员、运营审核人、素材管理员、FDE 团队。
- Workflow：活动简报 → 商品与素材准备 → 版式生成 → 人工编辑 → 审核 → 多渠道导出 → 发布复盘。
- Systems：商品信息库、素材库、创意工作台、审批记录、发布渠道。
- Datasets：商品字段、品牌规范、素材资产、渠道尺寸、审核意见。
- Artifacts：活动简报模板、品牌约束、版式规则、审批清单、发布记录。
- Metrics：首稿时间、修改轮次、准时交付率、可复用模板比例。

**关系主链**

```text
活动负责人 OWNS 活动简报 artifact
商品信息库 FEEDS 商品 dataset
素材管理员 OWNS 素材库 system
创意工作台 deployment PRODUCES 创意版本 artifact
运营审核人 APPROVES 发布版本
发布记录 EVIDENCES 准时交付 metric
```

### 10.4 案例公开规则

- 不公开未经授权的客户名称、人员、系统地址和敏感指标。
- 不把演示项目写成已上线案例。
- 不把方案建议写成结果证据。
- 所有数字必须有口径、日期和来源。
- 没有可公开数字时，可以描述已完成阶段和工件，不制造提升百分比。

## 11. 关系语法

### 11.1 关系类型

| 关系 | 含义 | 常见起点 → 终点 | 视觉表达 |
|---|---|---|---|
| `SPONSORS` | 提供业务授权与资源 | role → engagement | 粗实线，琥珀色 |
| `OWNS` | 对对象负责 | role → workflow/system/metric | 中粗实线 |
| `OPERATES` | 实际执行或使用 | role → workflow/system | 细实线 |
| `APPROVES` | 作出阶段或上线决定 | role → artifact/deployment | 末端带审批标记 |
| `READS_FROM` | 读取数据 | workflow/system → dataset | 带方向细线 |
| `WRITES_TO` | 写入数据 | workflow/system → dataset | 带方向细线 |
| `FEEDS` | 向下游提供输入 | system/dataset → workflow | 流向线 |
| `DEPENDS_ON` | 交付依赖 | engagement/artifact → system/role | 灰褐虚线 |
| `CONSTRAINS` | 限制方案或操作 | constraint → workflow/deployment | 红棕点划线 |
| `BUILDS` | 负责实现 | role → artifact/deployment | 琥珀细实线 |
| `PRODUCES` | 产生工件或结果 | workflow/deployment → artifact/evidence | 输出方向线 |
| `VALIDATES` | 验证事实或结果 | role/evidence → artifact/metric | 双线或验证标记 |
| `EVIDENCES` | 为指标或结论提供证据 | evidence → metric/decision | 高亮细线 |
| `BLOCKS` | 阻塞阶段或上线 | risk/constraint → stage/deployment | 风险色脉冲线 |
| `DEPLOYS_TO` | 发布到环境 | artifact → deployment/system | 粗方向线 |
| `HANDS_OFF_TO` | 责任移交 | role → role/deployment | 分段方向线 |
| `EXPANDS_TO` | 进入后续范围 | engagement → expansion/engagement | 外围增长线 |

### 11.2 关系约束

- 每条关系必须有 `source`、`target`、`type`、`reason` 和 `evidenceRef` 或 `sourceRef`。
- 公开页面可以隐藏证据内容，但不能隐藏关系为何存在。
- 不使用“相关”“协同”“赋能”等无法验证的关系类型。
- 跨簇关系只显示重要依赖、复用、移交和扩展，不把所有共同标签都画成线。
- 默认总览只显示一级关系；聚焦节点后再展开二级关系，控制视觉噪声。

## 12. 三维空间信息架构

### 12.1 总体空间模型

场景不是以个人为中心的太阳系，而是多个 FDE engagement 组成的企业交付网络。

推荐空间层级：

1. **全局交付网络**：显示所有公开 engagement、客户业务域和跨案例复用关系。
2. **案例簇**：每个 engagement 形成一个高密度局部星系。
3. **业务子簇**：角色、流程、系统、工件、指标和风险围绕 engagement 分组。
4. **节点聚焦层**：显示一个实体的上下游关系、证据和详情。

### 12.2 案例簇内部布局

每个案例簇采用稳定的空间语法：

- Engagement 位于簇中心。
- Business Problem 与 Metric 位于中心前上方，形成“目标面”。
- Workflow 形成横向主链，表示真实业务流。
- Role 分布在流程两侧，靠近其负责或操作的节点。
- System 与 Dataset 位于流程后方，形成“系统底盘”。
- Delivery Stage 构成从左后到右前的弧形时间骨架。
- Artifact 沿阶段附着，形成可审计的交付轨迹。
- Risk 与 Constraint 位于依赖附近，不能被放到无关角落。
- Evidence 与 Metric 位于部署后方，形成“结果面”。
- Expansion 位于簇外缘，指向下一次 engagement 或业务范围。

### 12.3 全局布局

- 各案例簇之间保持明显间距，但通过共享系统、共同交付模式或扩展关系连接。
- 采用确定性种子生成初始三维坐标，同一数据版本每次加载位置一致。
- 首次计算后执行有限次数的碰撞松弛，场景稳定后停止物理模拟。
- 不持续运行自由力导向模拟，避免节点长期漂移、标签抖动和设备发热。
- 重要跨案例关系可以形成“桥”，但不把共同标签全部连接成毛线球。

### 12.4 页面外壳

桌面端由五个层次组成：

1. **全屏 Three.js 场景**：占据主要视觉空间。
2. **顶部状态栏**：产品名、当前视图、案例数量、当前阶段和重置按钮。
3. **左侧导航台**：搜索、视图切换、案例列表、阶段筛选和关系图例。
4. **右侧检查器**：节点详情、责任、工件、证据、上下游和打开完整案例入口。
5. **底部导航提示**：旋转、缩放、聚焦、返回和键盘提示。

移动端保留真实三维场景，但采用受控交互：

- 默认锁定较小旋转范围，避免误触失焦。
- 单指旋转，双指缩放，点击聚焦。
- 详情使用底部抽屉。
- 提供“结构化列表”切换，保证低性能设备和辅助技术可完成同一任务。

## 13. 视图模式

同一套实体和关系支持四个视图，不复制数据。

### 13.1 Engagement 视图

默认视图。按案例簇组织所有业务对象，用于理解一项 FDE 交付的完整范围。

### 13.2 Delivery Stage 视图

将所有案例按阶段重新排布，回答：

- 哪些 engagement 正在发现、构建、试点或运行。
- 每个阶段有哪些已完成工件。
- 哪些项目被风险或审批阻塞。

### 13.3 System Topology 视图

突出系统、数据、流程和约束，弱化营销描述，回答：

- 需要读取和写入哪些数据。
- 哪些系统是关键依赖。
- 哪些边界需要安全、接口或人工审批。

### 13.4 Outcome Evidence 视图

突出 metric、evidence、deployment 和 accepted artifact，回答：

- 哪些结果已经有证据。
- 哪些只有目标，没有运行结果。
- 哪些案例已经进入稳定运行或扩展。

## 14. 核心交互

### 14.1 首次进入

- 先显示象牙白空间和淡化的全局关系骨架。
- 案例簇按前后层级进入，不使用粒子爆炸或无意义飞散。
- 核心 engagement 节点先出现，随后展开 workflow、system、artifact 和 evidence。
- 入场完成后停止自动镜头，立即把控制权交给用户。
- 首次访问只显示一次 5 秒内可理解的操作提示。

### 14.2 旋转、缩放和平移

- 拖动背景：围绕当前目标旋转。
- 滚轮 / 触控板 / 双指：镜头缩放。
- `Shift + 拖动`：平移视图。
- 双击空白或点击“总览”：返回全局构图。
- 相机距离、俯仰角和目标点都有安全范围，避免穿过节点或翻转迷失。

### 14.3 节点聚焦

点击节点后：

1. GSAP 驱动相机移动到适合阅读的观察位置。
2. 当前节点尺寸轻微放大并提高边框对比。
3. 一级上下游关系高亮。
4. 无关节点降至低透明度，但不完全消失，保留空间方向感。
5. 右侧检查器显示类型、状态、责任、阶段、关系理由和证据状态。
6. URL 写入 `view`、`case` 和 `node`，支持分享和后退恢复。

### 14.4 案例聚焦

- 从左侧选择案例后，镜头移动到该案例簇中心。
- 其他案例缩小并后退，跨案例桥保持可见。
- 用户可以切换“业务流”“系统底盘”“交付证据”三个局部层次。
- 返回总览时恢复原相机位置和筛选，不重新随机布局。

### 14.5 路径追踪

用户可选择预定义业务路径，例如：

```text
Business Problem
→ Workflow
→ Dataset / System
→ Delivery Artifact
→ Deployment
→ Evidence
→ Metric
→ Expansion
```

路径播放规则：

- GSAP 沿真实关系逐段高亮，不生成新的装饰航线。
- 每一步显示关系动词和业务理由。
- 用户可以暂停、前进、后退和退出。
- 减少动态效果模式下改为静态分步高亮。

### 14.6 搜索与筛选

支持按以下字段搜索：

- 案例名称。
- 业务问题。
- 业务流程。
- 系统或数据源。
- 角色。
- 工件。
- 指标。
- 风险。

支持按以下维度筛选：

- 交付阶段。
- 节点类型。
- 交付状态。
- 行业或业务域。
- 公开级别。
- 是否已有结果证据。

筛选后不删除节点，只降低无关对象的视觉权重，并提供“仅显示匹配关系”开关。

## 15. 视觉方向：暖白企业系统制图

### 15.1 视觉概念

推荐概念名称：

**Ivory Systems Cartography / 象牙白企业系统制图**

它应同时具有：

- 录屏中高密度三维网络的空间震撼。
- 企业架构图的严谨和可读性。
- 现场工程图的层次、标注和证据感。
- AILA 既有暖白、琥珀橙和克制动效语言。

### 15.2 色彩系统

| 用途 | 推荐色 | 说明 |
|---|---|---|
| 场景背景 | `#F7F3EA` | 暖象牙白，主空间底色 |
| 近景雾层 | `#FFFDF8` | 控制深度，不做黑色雾 |
| 主文字 | `#111111` | 标题、关键业务对象 |
| 正文 | `#444444` | 详情与关系说明 |
| 辅助文字 | `#666666` | 状态、来源、次级标签 |
| 主边框 | `#E5E1D8` | 面板与默认节点边界 |
| 品牌高亮 | `#D97706` | 当前焦点、CTA、主要交付路径 |
| 关系线 | `#B8AEA0` | 默认结构关系 |
| 数据 / 系统 | `#6F7F78` | 低饱和灰绿 |
| 工件 / 证据 | `#8A7356` | 纸张与档案感 |
| 风险 / 阻塞 | `#A6543D` | 克制红棕，不使用高亮警报红 |
| 已运行 | `#53715F` | 稳定运行和接受状态 |

### 15.3 节点造型

- `engagement`：实心球体加双层轨道环，作为案例簇核心。
- `business_problem`：较大圆角多面体，强调问题边界。
- `workflow`：沿主链排列的扁球或圆角胶囊节点。
- `role`：较小实体球，附带角色缩写标签。
- `system`：低饱和金属感立方或切角节点。
- `dataset`：半透明层叠球或薄片节点。
- `artifact`：象牙纸张色小型多面体。
- `metric`：带刻度环的圆形节点。
- `evidence`：高亮小节点，具有明确验证标记。
- `risk` / `constraint`：红棕描边节点，不使用持续闪烁。

节点造型要在缩小状态下仍能通过轮廓区分，不能只依赖颜色。

### 15.4 标签

- 总览只显示 engagement、business problem 和关键 workflow 标签。
- 聚焦后显示一级邻居标签。
- 标签使用屏幕空间避让，避免被三维透视压缩到不可读。
- 标签内容最多两行，超长名称进入检查器。
- 不显示漂浮的宣传口号。

### 15.5 关系线

- 默认线条细、低对比，建立密度而不抢夺注意力。
- 选中节点后，相关关系线提高宽度、对比和方向标记。
- 主交付路径使用琥珀橙，风险和阻塞使用红棕，数据流使用灰绿。
- 跨案例桥线比簇内关系更长、更淡，并带关系标签。
- 不使用无业务含义的随机轨道和装饰连接。

### 15.6 空间质感

- 使用轻微环境光、柔和方向光和低强度阴影建立体积。
- 使用暖白深度雾控制远景密度。
- 可加入极低对比的纸张颗粒或制图网格，但不能模拟星空粒子。

## 17. Three.js 技术方向

项目已经包含 `three` 和 `@types/three`，第一版直接使用 Three.js，不再先做二维 SVG 版本，也不额外引入 React Three Fiber。

### 17.1 场景职责

- `WebGLRenderer`：三维场景主渲染器。
- `PerspectiveCamera`：总览、案例和节点聚焦镜头。
- `Scene`：管理雾、灯光、节点组和关系组。
- `InstancedMesh`：批量渲染普通小节点，减少 draw call。
- 独立 Mesh：渲染需要特殊形态或高亮的核心节点。
- `BufferGeometry` / `LineSegments`：渲染默认关系网络。
- Three.js examples 中的宽线能力：只用于聚焦路径和关键跨案例桥。
- `Raycaster`：节点 hover、点击和聚焦。
- `CSS2DRenderer`：渲染屏幕空间标签和必要的可访问 DOM 镜像。

### 17.2 React 边界

- 页面外壳、筛选、检查器、URL 状态和结构化列表由 React 管理。
- Three.js 场景放入独立客户端组件，按路由动态加载，避免服务端访问 DOM。
- React 只把数据版本、筛选条件、选中 ID 和视图模式传入场景控制器。
- 每帧相机和对象更新留在 Three.js 渲染循环，不通过 React state 驱动。
- 组件卸载时释放 geometry、material、texture、renderer、事件监听和动画上下文。

### 17.3 布局策略

推荐两阶段布局：

1. 纯 TypeScript 根据案例、实体类型和交付阶段生成确定性初始坐标。
2. 场景初始化时执行有限次数的局部碰撞松弛，然后冻结位置。

布局必须满足：

- 同一案例实体保持成簇。
- Workflow 具有可读方向。
- Stage 具有稳定时间顺序。
- System / Dataset 形成可识别的后层。
- Risk 靠近受影响对象。
- Evidence 靠近被证明的 Metric 或 Artifact。

### 17.4 性能预算

标准版建议预算：

- 首批公开案例：3 至 5 个。
- 节点：80 至 160 个。
- 默认可见关系：120 至 260 条。
- 聚焦时高亮关系：不超过 30 条。
- 普通桌面目标：交互期间接近 60 FPS。
- 中端移动设备目标：交互期间不低于 30 FPS。
- WebGL 场景按需加载，不阻塞页面基础文本和导航出现。
- 页面隐藏或浏览器标签失焦时降低或暂停渲染频率。

超过预算时优先采用实例化、标签分级、关系分层和视锥裁剪，不先降低信息真实性。

## 18. GSAP 动画方向

项目当前没有 GSAP。进入实现阶段时只新增：

- `gsap`
- `@gsap/react`

Framer Motion 继续服务已有普通界面；FDE Galaxy 的三维镜头和关系动画使用 GSAP，避免两套动画引擎同时控制同一对象。

### 18.1 GSAP 负责的动画

- 首次入场的案例簇展开。
- 总览、案例和节点之间的相机航行。
- 聚焦时节点、关系和标签的权重过渡。
- 交付阶段视图与系统拓扑视图之间的布局过渡。
- 关系路径的逐段高亮和方向追踪。
- 检查器与三维聚焦的同步时序。

### 18.2 GSAP 不负责的内容

- 不用 GSAP 持续驱动每一帧的场景更新。
- 不给所有节点添加永久漂浮、呼吸或旋转。
- 不用动画掩盖布局错误或信息层级问题。
- 不在 React render 中创建 timeline。

### 18.3 生命周期与性能

- 使用 `useGSAP` 或 `gsap.context()` 在组件挂载后创建动画。
- 组件卸载、案例切换和路由离开时 `revert()` 或 `kill()`。
- 相机和节点动画优先修改位置、旋转、缩放和透明度。
- 不在动画回调中高频写 React state。
- 同一对象的新聚焦动画使用 overwrite，避免镜头命令叠加。
- 所有主要动画提供 `prefers-reduced-motion` 分支。

### 23.3.1 文案验收

- 所有主要文案优先说明业务，而不是说明“宇宙、星团、发光”等视觉概念。
- FDE 定义采用“负责对象 + 交付动作 + 生产结果 + 持续责任”的结构。
- 六个交付阶段分别说明输入、关键动作和可验收产出，避免只写抽象动词。
- 案例节点必须给出业务流程、交付结果或验证证据；没有证据时明确标注为实验或档案。
- 图谱视觉规则只出现在操作提示，不占用业务详情的主要阅读位置。

### 23.3.2 节点内容与点击契约

- 所有出现在关系线上的节点都必须有稳定 `id`、标题、英文标识、摘要、详细说明、状态和标签，不允许存在纯装饰空节点。
- 单击节点先在星系内打开详情面板，用户可以在不离开场景的情况下理解节点作用。
- 每个节点同时拥有稳定独立地址 `/toni-universe/[nodeId]`，用于后续承载业务背景、FDE 交付动作、生产证据、指标、截图和复用资产。
- 节点档案页自动展示直接相连的上下游节点，关系来自同一份图谱数据，不单独维护第二套关系。
- 节点没有正式案例页时仍可进入节点档案；案例项目链接属于补充入口，不作为节点内容存在的前提。

### 23.4 交互验收

- 旋转、缩放、平移、聚焦和返回行为可预测。
- 快速连续点击不同节点不会卡住或飞向错误位置。
- 选中状态在场景、检查器、URL 和列表中一致。
- 触控区域足够，移动端不会因旋转手势阻止查看详情。
- 所有异步加载、错误、空数据和降级状态有明确反馈。

### 23.5 工程验收

- `npm run test:baseline` 通过。
- `npm run lint` 通过。
- `npm run build` 通过。
- TypeScript 不新增 `any`。
- 不新增 `console.log`、`TODO`、`FIXME`、本机路径或密钥。
- 不存在未释放的 Three.js geometry、material、renderer 或事件监听。
- GSAP timeline 在卸载和切换时正确清理。
- 场景在重复进入、退出和聚焦后无持续内存增长。

## 24. 主要风险与控制方式

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 视觉压过业务 | 用户只记得三维效果，不理解交付 | 所有节点和关系必须来自业务本体，详情始终显示关系理由 |
| 密度失控 | 场景成为无法阅读的毛线球 | 默认分层显示关系，聚焦后再展开二级网络 |
| 节点尺寸失真 | 视觉最大节点并非业务核心 | 使用统一权重模型并在内容评审中检查 |
| 关系缺少证据 | 图看起来完整但无法解释来源 | 每条关系强制 `reason` 与 `sourceRef` |
| 案例宣传化 | 只有结果口号，没有过程和工件 | 强制展示阶段、责任、工件、部署和证据 |
| 客户信息泄露 | 客户名称、数据或系统被误公开 | 公开级别在数据生成阶段过滤，阶段 0 人工审批 |
| 结果指标失真 | 演示值被写成真实收益 | 指标必须有口径、日期、责任人和证据状态 |
| Three.js 生命周期泄漏 | 路由切换后 GPU 和事件仍占用 | 创建与 dispose 成对，加入重复进入退出测试 |
| GSAP 动画冲突 | 连续操作导致镜头抖动或错位 | 单一相机控制器、overwrite、切换时 kill/revert |
| 移动端误触 | 旋转和滚动冲突 | 受控手势、底部抽屉、列表模式 |
| 低性能设备卡顿 | 标签和关系过多导致掉帧 | 实例化、关系分层、标签分级、自动降级 |
| 用户空间迷失 | 聚焦后不知道自己在哪里 | 保留背景方向、面包屑、总览按钮和相机边界 |
| WebGL 不可用 | 页面完全空白 | 结构化列表作为正式等价路径 |
| 范围继续膨胀 | 变成 CRM、项目管理或知识库 | 第一版只读、本地数据、公开解释型页面 |
| 技术方案脱离项目 | 引入过多框架和状态层 | 直接使用现有 Three.js，只增加 GSAP 相关依赖 |

## 25. 已锁定决策

以下决策应视为本方案的默认实施基线：

1. 核心业务定位为 Enterprise FDE，不再是 Toni / 泛技术作品集。
2. 页面展示名使用 `FDE Delivery Galaxy`，不使用 `Toni Universe` 作为主标题。
3. Canonical route 为 `/toni-universe`。
4. 最终体验必须是真实三维节点关系场景，不以二维 SVG 作为正式产品形态。
5. 视觉采用深空工业感的粒子星系：蓝黑背景、冷青结构、钢蓝关系、旧金核心与少量铜色证据节点；不使用粉紫霓虹作为主色。
6. 首批图谱围绕真实 engagement、业务问题、流程、系统、角色、阶段、工件、部署和证据组织。
7. Three.js 负责场景，GSAP 负责相机和状态过渡，React 负责页面外壳和业务状态。
8. 第一版直接使用项目已有 Three.js，不引入 React Three Fiber。
9. 第一版只读，使用本地强类型数据，不接入外部图数据库或动态关系生成。
10. 移动端保留受控三维体验，同时提供完整列表降级。
11. 公开数据在进入客户端前完成脱敏和过滤。
12. 所有结果必须标明证据状态，不制造未验证指标。

## 26. 后续数据确认事项

当前三维样板已经实现。继续扩充真实企业案例前，需要确认以下业务数据：

1. 是否需要额外提供 `/fde` → `/toni-universe` 的永久兼容跳转。
2. 首批三个案例中，哪些名称、工件截图和指标可以公开。
3. 是否存在第四或第五个已经上线、适合形成跨案例桥的 FDE engagement。
4. 结果指标是公开具体数值、区间、相对变化，还是只公开证据状态。
5. 案例详情继续链接现有作品页，还是为 FDE 单独建立详情页。
6. 是否允许公开客户侧角色名称，还是统一使用角色类型。

这些事项不影响当前三维体验，但会决定正式公开版本的案例深度、证据强度和可披露范围。

## 27. 完成定义

本项目只有同时满足以下条件才算完成：

- 产品文案、信息架构和默认视图都以 FDE 交付为中心。
- 页面包含至少三个真实案例簇和一组可解释的跨案例关系。
- 场景具有真实三维深度、密集节点、尺寸差异、关系线、旋转、缩放和聚焦。
- 用户能从业务问题追踪到流程、角色、系统、阶段、工件、部署、证据和指标。
- 所有关系节点均可点击、可阅读，并可进入稳定的独立节点档案地址。
- 所有公开关系都有来源或业务理由。
- 桌面、移动、键盘、减少动态效果和 WebGL 降级路径可用。
- 自动化门禁、构建、浏览器 QA 和公开部署验证完成。
- 原有页面未被无关改造破坏。
